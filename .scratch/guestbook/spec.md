# 미니 방명록 MVP

## Problem Statement

방문자가 회원가입이나 로그인 없이 가볍게 인사를 남기고, 다른 사람이 남긴 글을 최신순으로 볼 수 있는 곳이 없다. 동시에 계정이 없으므로, 자기가 남긴 글을 나중에 고치거나 지우고 싶을 때 "이 글이 내 글"임을 증명할 방법이 필요하고, 남이 내 글을 고치거나 지우지 못해야 한다.

## Solution

한 페이지짜리 방명록을 만든다. 누구나 작성자 이름, 메시지, 글 비밀번호를 입력해 방명록 글을 남길 수 있고, 모든 방명록 글이 작성 시각 기준 최신순으로 보인다. 각 방명록 글에는 수정·삭제 버튼이 있으며, 글 비밀번호를 맞게 입력한 글쓴이만 메시지를 수정하거나 글을 삭제할 수 있다. 비밀번호가 틀리면 요청이 거부되고 그 이유가 화면에 표시된다. 화면에는 개발자 이름과 학번(정윤서, 202404307)이 표시된다.

## User Stories

1. 방문자로서, 페이지를 열자마자 모든 방명록 글 목록을 보고 싶다, 그래야 다른 사람들이 남긴 말을 읽을 수 있다.
2. 방문자로서, 가장 최근에 작성된 방명록 글이 맨 위에 보이길 원한다, 그래야 새 소식을 먼저 볼 수 있다.
3. 방문자로서, 각 방명록 글의 작성자 이름을 보고 싶다, 그래야 누가 남긴 글인지 알 수 있다.
4. 방문자로서, 각 방명록 글의 작성 시각을 한국 시간으로 보고 싶다, 그래야 언제 쓴 글인지 헷갈리지 않는다.
5. 방문자로서, 메시지의 줄바꿈이 입력한 그대로 보이길 원한다, 그래야 글쓴이가 의도한 모양대로 읽을 수 있다.
6. 방문자로서, 방명록 글이 하나도 없을 때 비어 있다는 안내를 보고 싶다, 그래야 화면이 고장 난 게 아님을 알 수 있다.
7. 방문자로서, 화면에서 이 방명록을 만든 개발자의 이름과 학번을 보고 싶다, 그래야 누구의 작품인지 알 수 있다.
8. 방문자로서, 회원가입 없이 작성자 이름, 메시지, 글 비밀번호만 입력해 방명록 글을 남기고 싶다, 그래야 부담 없이 참여할 수 있다.
9. 방문자로서, 방명록 글을 남기면 목록 맨 위에 바로 보이길 원한다, 그래야 등록이 됐음을 확인할 수 있다.
10. 방문자로서, 작성에 성공하면 입력란이 비워지길 원한다, 그래야 같은 글을 실수로 두 번 올리지 않는다.
11. 방문자로서, 작성자 이름·메시지·글 비밀번호 중 하나라도 비어 있거나 공백뿐이면 거부되고 안내받고 싶다, 그래야 빈 글이 쌓이지 않는다.
12. 방문자로서, 입력 검증에 실패해도 이미 입력한 내용이 지워지지 않길 원한다, 그래야 다시 입력하지 않아도 된다.
13. 방문자로서, 작성자 이름은 20자, 메시지는 500자를 넘게 입력할 수 없길 원한다, 그래야 목록이 지나치게 길어지지 않는다.
14. 글쓴이로서, 내 글 비밀번호가 원문 그대로 저장되지 않길 원한다, 그래야 저장소가 유출돼도 비밀번호가 드러나지 않는다.
15. 방문자로서, 목록을 볼 때 다른 사람의 글 비밀번호나 그 해시가 전달되지 않길 원한다, 그래야 비밀번호를 알아내 남의 글을 건드릴 수 없다.
16. 글쓴이로서, 내 방명록 글의 수정 버튼을 누르면 그 글 바로 아래에 새 메시지와 글 비밀번호 입력란이 펼쳐지길 원한다, 그래야 다른 페이지로 이동하지 않고 고칠 수 있다.
17. 글쓴이로서, 수정 입력란에 기존 메시지가 미리 채워져 있길 원한다, 그래야 일부만 고칠 수 있다.
18. 글쓴이로서, 올바른 글 비밀번호를 입력하면 메시지가 바뀌길 원한다, 그래야 오타나 내용을 정정할 수 있다.
19. 글쓴이로서, 수정해도 작성자 이름과 작성 시각은 그대로이길 원한다, 그래야 원래 누가 언제 쓴 글인지 유지된다.
20. 방문자로서, 어떤 글이 수정돼도 목록 순서가 바뀌지 않길 원한다, 그래야 목록이 예측 가능하다.
21. 방문자로서, 남의 글에 틀린 글 비밀번호로 수정을 시도하면 거부되길 원한다, 그래야 남의 글을 바꿀 수 없다.
22. 글쓴이로서, 글 비밀번호가 틀려 수정이 거부되면 "비밀번호가 일치하지 않습니다."라는 안내를 그 글 옆에서 보고 싶다, 그래야 왜 안 됐는지 알 수 있다.
23. 글쓴이로서, 수정이 거부돼도 내가 입력한 새 메시지가 유지되길 원한다, 그래야 비밀번호만 다시 입력하면 된다.
24. 글쓴이로서, 새 메시지를 비우고 수정하려 하면 거부되고 안내받고 싶다, 그래야 실수로 빈 글이 되지 않는다.
25. 글쓴이로서, 수정을 취소하고 입력란을 닫을 수 있길 원한다, 그래야 마음이 바뀌었을 때 되돌릴 수 있다.
26. 글쓴이로서, 내 방명록 글의 삭제 버튼을 누르면 그 글 아래에 글 비밀번호 입력란이 펼쳐지길 원한다, 그래야 실수로 바로 삭제되지 않는다.
27. 글쓴이로서, 올바른 글 비밀번호를 입력하면 방명록 글이 목록에서 사라지길 원한다, 그래야 남기고 싶지 않은 글을 지울 수 있다.
28. 방문자로서, 남의 글에 틀린 글 비밀번호로 삭제를 시도하면 거부되길 원한다, 그래야 남의 글을 지울 수 없다.
29. 글쓴이로서, 글 비밀번호가 틀려 삭제가 거부되면 "비밀번호가 일치하지 않습니다."라는 안내를 그 글 옆에서 보고 싶다, 그래야 왜 안 됐는지 알 수 있다.
30. 글쓴이로서, 삭제를 취소하고 입력란을 닫을 수 있길 원한다, 그래야 마음이 바뀌었을 때 되돌릴 수 있다.
31. 방문자로서, 이미 삭제된 방명록 글을 수정·삭제하려 하면 "이미 삭제된 글입니다."라는 안내를 보고 싶다, 그래야 다른 탭에서 지운 상황을 이해할 수 있다.
32. 방문자로서, 글 비밀번호 확인이 브라우저가 아니라 서버에서 이뤄지길 원한다, 그래야 개발자 도구로 검증을 우회할 수 없다.
33. 방문자로서, 배포된 주소에서 작성·조회·수정·삭제가 모두 동작하길 원한다, 그래야 실제로 방명록을 쓸 수 있다.

## Implementation Decisions

- **스택**: Next.js 16 App Router + TypeScript, Neon Postgres, Vercel 배포. DB 접근은 `@neondatabase/serverless`로 SQL을 직접 작성하고 ORM은 쓰지 않는다. 연결 정보는 `DATABASE_URL` 환경 변수 하나로 받는다(로컬 `.env.local`, 배포는 Vercel 환경 변수).
- **스키마**: 테이블 하나. 테이블은 앱이 만들지 않고 Neon SQL Editor에서 직접 한 번 실행한다(로컬과 배포가 같은 DB를 공유).

  ```sql
  CREATE TABLE entries (
    id            SERIAL PRIMARY KEY,
    name          VARCHAR(20)  NOT NULL,
    message       VARCHAR(500) NOT NULL,
    password_hash TEXT         NOT NULL,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
  );
  ```

- **방명록 글 모듈 (깊은 모듈 하나)**: 방명록 글에 대한 모든 DB 접근과 글 비밀번호 검증을 한 모듈에 모은다. 인터페이스:
  - 목록 조회: 모든 방명록 글을 작성 시각 내림차순으로 반환. 반환 형태에 `password_hash`는 **포함하지 않는다** (SELECT 단계에서 제외).
  - 작성: 작성자 이름, 메시지, 글 비밀번호를 받아 비밀번호를 해시해 저장.
  - 메시지 수정: id, 새 메시지, 글 비밀번호를 받아 결과를 `성공 | 비밀번호 불일치 | 글 없음` 중 하나로 반환.
  - 삭제: id, 글 비밀번호를 받아 결과를 `성공 | 비밀번호 불일치 | 글 없음` 중 하나로 반환.
  - 수정·삭제는 모두 "id로 해시를 조회 → 비교 → 일치할 때만 실행" 순서를 따른다.
- **비밀번호 해시**: `bcryptjs`(이미 설치됨), cost 10. 비교는 서버에서만 한다.
- **서버 로직**: Server Actions(Server Functions)를 쓴다. Route Handler는 만들지 않는다. 각 액션은 폼 데이터를 받아 공백 제거·빈값 검증을 하고 방명록 글 모듈을 호출한 뒤, 성공 시 페이지를 재검증(revalidate)하고 실패 시 에러 문구를 담은 상태를 반환한다.
- **입력 규칙**: 작성자 이름·메시지·글 비밀번호 모두 필수(앞뒤 공백 제거 후 빈값이면 거부). 길이 제한은 입력란의 `maxLength`(이름 20, 메시지 500)로 걸고, DB 컬럼 길이가 최종 방어선이다. 글 비밀번호 최소 길이 규칙은 없다.
- **UI**: 한 페이지. 위에서부터 헤더(`방명록 · 개발자: 정윤서 (202404307)`) → 작성 폼 → 목록. 작성 폼과 각 글의 수정·삭제 폼은 클라이언트 컴포넌트로 만들고 `useActionState`로 에러 문구를 표시한다. 수정·삭제 버튼을 누르면 해당 글 아래에 인라인 폼이 펼쳐지고, 취소 버튼으로 닫는다.
- **에러 문구**: 비밀번호 불일치 → "비밀번호가 일치하지 않습니다." / 글 없음 → "이미 삭제된 글입니다." / 빈값 → 어떤 필드가 비었는지 알려 주는 문구. 실패 시 사용자가 입력한 값은 유지한다.
- **시간 표시**: 작성 시각은 `ko-KR` 로캘, `Asia/Seoul` 시간대로 포맷한다(Vercel 서버는 UTC).
- **렌더링**: 목록 페이지는 요청마다 DB를 읽는 동적 페이지여야 한다(빌드 시점에 정적으로 굳지 않게).

## Testing Decisions

- 좋은 테스트는 외부에서 관찰 가능한 동작만 확인한다: "올바른 비밀번호면 메시지가 바뀐다", "틀리면 거부되고 안내가 보인다", "목록 응답에 비밀번호 해시가 없다" 등. 내부 쿼리 문자열이나 컴포넌트 구조는 검증 대상이 아니다.
- **테스트 경계(seam)**: 방명록 글 모듈의 인터페이스 하나. 수정·삭제의 결과 타입(`성공 | 비밀번호 불일치 | 글 없음`)이 핵심 검증 포인트다.
- 시간 제약(남은 시험 시간 60분)으로 **자동화 테스트 프레임워크는 도입하지 않는다.** 대신 각 티켓 완료 시 로컬과 Vercel 배포 URL에서 아래 체크리스트를 직접 확인한다.
  - 작성 → 목록 맨 위에 반영, 작성 시각 표시
  - 빈값 작성 → 거부 + 안내
  - 수정: 올바른 비밀번호 → 메시지 변경 / 틀린 비밀번호 → 거부 + 안내
  - 삭제: 올바른 비밀번호 → 삭제 / 틀린 비밀번호 → 거부 + 안내
  - 목록 순서가 수정 후에도 유지됨
- 기존 테스트 선례는 없다(빈 create-next-app 프로젝트).

## Out of Scope

- 회원가입, 로그인, 관리자 기능
- 작성자 이름 수정
- 수정 시각(`updated_at`) 기록 및 "수정됨" 표시
- 페이지네이션, 무한 스크롤, 검색
- 소프트 삭제(삭제는 DB에서 완전히 제거)
- 글 비밀번호 최소 길이·복잡도 규칙, 비밀번호 찾기
- 스팸 방지, 요청 횟수 제한
- 글자 수 카운터 등 부가 UI
- 자동화 테스트

## Further Notes

- **배포가 최우선이다**: 채점상 Vercel 배포 URL이 동작하지 않으면 0점이므로, 첫 티켓에서 목록 화면만으로도 먼저 배포를 확인하고 이후 티켓마다 push해서 배포를 확인한다.
- Vercel 프로젝트에 `DATABASE_URL`은 이미 등록돼 있다. GitHub 저장소는 제출 전에 **public**이어야 한다.
- 이 프로젝트의 Next.js는 학습 데이터와 다를 수 있으므로, 구현 전에 `node_modules/next/dist/docs/`의 해당 가이드(Server Functions, `useActionState`, revalidate, 동적 렌더링)를 확인한다.
- 용어는 `GLOSSARY.md`를 따른다(방명록 글, 작성자 이름, 메시지, 글 비밀번호, 작성 시각, 글쓴이).
